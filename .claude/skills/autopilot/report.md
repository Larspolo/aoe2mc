# Autopilot: the run report (step 8)

Read this file before the report of step 8 (part of the `autopilot` skill, #1700).

No open issue with label `agent-status` (step 1.1): make it (title "Agent status", body: the state comment below and
an empty `### Process changes`). The dashboard workflow fills in the rest.

The dashboard in the body of the status issue is generated by `tools/dashboard.py`. Run `python3 tools/dashboard.py`
after your report (the workflow `dashboard.yml` runs it every 10 minutes, #2168). Do not write
"Waiting for you", "Working on", "Next up" or "Recently done": the script makes them from GitHub.
`tools/report.py --post` (below) sets the state comment: `last_run` now and `runs` + 1, the other keys stay
(`last_review`, `review_prs`, `last_roadmap`: the reviews, #898, #2039; #1701). Do not edit it by hand.
In the body, change only one part by hand and keep the rest as it is (read the body just before the change,
other runs change it too):
- The section `### Process changes`: add a line `- <date>: <what changed in the skills, CLAUDE.md or
  LEARNINGS> (PR #n) — before: <numbers>` at the top, keep the last 5. When the change targets a number of
  `tools/health.py` (phase minutes, conflicts, takeovers, quota per PR), write that number now for the last 50 merged
  PRs (`tools/health.py`, for example "report 10 % of the run minutes / 50 PRs"), so that the `improve` skill can
  check it later on the same amount of work (#1738, #2039). A pitfall line
  (`docs/LEARNINGS.md`, a doc line) gets `— before: -`.

Then add one short report: what you did and what is next. `--post` adds it to the branch `metrics` (`runs/`), not as
a comment on the status issue (2026-10-29; only when no push goes through, it comments). Write it with one command (#1701): `python3 tools/report.py --usage "<the Usage: line of step 1.2>" --text "<what you
did, what is next>" --ticket N --size S --result "pr #M" --setup 0 --checks K --checks-min C --sinks "<list or none>"
--post` (repeat the ticket options for each ticket,
in the same order). It adds the release bar, the `Tokens:` line and the footer in the format below. Without `--post`
it only prints the report. A question for the owner goes on its
issue, not here (`owner.md`).
End it with one metrics line for each ticket of the run (the `improve` skill reads these lines):

    Metrics: ticket #<n> · <size> · <merged|pr #n|blocked|needs-human|none> · <minutes> min · setup <m> min · checks <k> · checks <c> min · time sinks: <list or "none"> · phases read <m> · claim <m> · code <m> · verify <m> · ci <m> · conflict <m> · report <m>

Example: `Metrics: ticket #876 · size:S · merged · 45 min · setup 0 min · checks 2 · checks 6 min · time sinks: none ·
phases read 8 · claim 1 · code 18 · verify 9 · ci 0 · conflict 5 · report 4` (one line).

Result: `pr #n` when you pushed PR #n and Automerge merges it later (the usual case: you report before the merge);
`none` only when the run stopped without a PR. `tools/health.py` counts the `pr #n` lines by the present PR state (#902).
`tools/report.py` puts the output of `python3 tools/release.py` (the release bar of each goal, #879) above the
`Usage:` line, when the project has that tool (#1963).
Below the metrics lines, put the output of `python3 tools/tokens.py` (one `Tokens:` line for the run: the tokens of
this session and its largest sinks; run it just before the comment). `report.py` adds it, the `Calls:` line and the `Run:` line
(the session, the start, the model, the eq of each phase and ticket, the lane). `tools/health.py` adds these lines, and the
`improve` skill uses them as one source to find the bottleneck.
Put the `Usage:` line of step 1.2 above the metrics lines, unchanged: `tools/health.py` measures the quota use of one
run per hour from pairs of these lines, and `tools/usage.py --target` uses that value (#462).
`setup`: minutes from the start time (step 4) to the claim of the first ticket (0 for later tickets).
`checks <k>`: rounds of the `verify` skill before the push; `checks <c> min`: their minutes in total.
`phases` (#899): whole minutes of the ticket in each phase. `report.py` measures them in the transcript
(`tokens.py --phases`): do not give `--phases` (the guesses of the runs were 2 to 6 times too large, 2026-10-28). `read` (feedback, triage, the ticket and the code), `claim` (pick and claim), `code` (change and tests),
`verify` (the checks of the `verify` skill), `ci` (wait for or fix CI after the push), `conflict` (merges with main),
`report` (PR text, run report, process step 9). Keep the fields in this order: `tools/health.py` sums them.

Do not post a report when nothing changed.
